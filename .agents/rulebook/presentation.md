# Presentation requirements

Use Astro/Starlight with readable Markdown content loaded directly from `content/en/`. The website is a presentation of the canonical content, not a separate source of API facts.

## Reading experience

Provide hierarchical navigation, a comfortable main column, an in-page contents list, visible search, light/dark themes, and responsive navigation. Use the InnoEngine logo with its author credit and separate license. Do not copy Godot branding or invent another logo source.

Derive one navigation tree from canonical categories and authored navigation. Publish content-addressed child lists as shared static resources; each page renders only root entries. Load children on expansion and preserve reader choices. Every top-level group is disclosure-only with a chevron; its label does not navigate. Below the first level, ordinary groups are disclosure-only and a group with a registered home has a separate left-aligned square plus/minus button and a linked label, without a duplicate home child. Both expansion and collapse animate, respecting reduced-motion preferences. Center controls against the complete label row, including wrapped labels. Highlight the complete expanded/current row with a translucent background and bold underlined label; hover alone must not change text weight. Leave vertical space between row highlights and equal horizontal clearance from the left tree line and the right content/scrollbar edge. On desktop, animate the left sidebar's width to fit visible unwrapped labels up to half the viewport, then wrap; preserve the normal right TOC width and use the full-width mobile menu. Build restored descendants before revealing their branch so asynchronous loading cannot interrupt the opening layout. API types sort alphabetically. No-JavaScript readers retain ordinary category tables and essential content. Validate shared navigation once and each page's own HTML, declarations, links and anchors.

All API pages start with the actual source summary below the title and above the status panel, including manually owned pages. The summary is a generated fact and is not stored in the editable fragment body. Generate remarks, parameters, returns, exceptions and examples as readable Markdown sections, at the same heading level as Declaration. Manual ownership can replace these body sections but never the generated summary or declaration. Preserve manually owned prose. Show an icon-and-title status band above required contracts: pale yellow Synced for XML-managed prose, pale red Outdated for manual prose with changed contracts or requested review, and pale green Verified for manual prose without pending review. Verified is not a machine guarantee of semantic correctness. Separate generated and author-editable API frontmatter with YAML comments and a blank line. Preserve authored body bytes when updating metadata; omit body editing links and target/configuration dumps. Put Project/API/Scope, Inherits and Implements in one compact paragraph separated by hard line breaks (before Declaration). Put source provenance directly above the footer's GitHub editing link. Preserve applicability facts in canonical references and query provenance.

Keep keyboard focus visible. Use semantic headings, meaningful accessible names, and sufficient contrast. Ordinary prose must not overflow horizontally. Signatures, code, and data tables may scroll inside their own containers. Necessary information must remain available without client JavaScript.

Theme components own layout. Ordinary content does not import MDX components or execute scripts. Important constraints must remain visible without expanding a disclosure. Supported Markdown must agree between the canonical parser, GitHub reading, and rendered anchors.

## Verification

Inspect landing, manual, tutorial, API, search, and error states in both themes at desktop, tablet, and mobile widths. Verify deep links under the documentation base path on the selected host, keyboard navigation, copy controls, and code/table overflow. A successful static build alone is not visual or accessibility acceptance.
