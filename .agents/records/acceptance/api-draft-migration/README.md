# API content migration

This register tracks the approved move from project/compiler-context pages to one independently owned fragment per type and member. It is not a hosted publication receipt or a semantic certification of every XML description.

## Inputs and dispositions

- `baseline.json` inventories 3,655 prior active pages with their original content identities and symbol associations.
- `migration.json` assigns every inventoried page a destination or an explicit scope retirement. It records six preserved manual fragments, including the protected IdentityObject constructor explanation absent from XML.
- `original-generation/` retains the original generator ownership reports byte for byte. Earlier review reports under `reference/provenance/` also retain their original bytes; the migration checker follows this register to current destinations.
- The API registry contains 18,335 distinct type/member identities. Runtime availability in Editor can yield additional surface-qualified coverage without duplicating authored prose.
- All 252 project guides remain, classified as engine architecture, backend integration, or test/fixture guidance. Backend and fixture member references have been removed from the API catalog.

The two historical macOS captures remain explicitly historical. A coherent current-source export from a real macOS producer is still required before this input can be published as a new complete API package.

## Retired implementation and regression ownership

`scripts/Update-ApiReference.ps1` and its dedicated test suite have been removed. The canonical engine documentation library now owns synchronization, XML rendering, fragment composition and queries.

| Previous responsibility | Current verification |
| --- | --- |
| Binding identity, unchanged export and source provenance | Package import tests reject corrupt/mixed inputs and preserve revision-only no-ops |
| Script context identity | Declared Scope and actual projection tests retain one body with exact availability |
| Declarations and shared constraints | Catalog/query composition tests verify generated declarations, visible required contracts and exact member provenance |
| Authored files and existing unowned pages | Per-symbol manual preservation, unknown marker and unregistered-file rejection tests |
| XML formulas, indentation and embedded markup | Formula/example boundary and fence preservation tests |
| Nested lists and following obligations | Nested XML list preservation tests |
| Unknown XML, unsafe entities and malformed tables | Failure-before-write tests retain the last good prose |
| Escaping output paths and approved API scope | Path boundary tests and five actual excluded-owner synchronization cases |
| Large-type splitting and enum grouping | Superseded by the approved independent member-fragment model; complete type composition retains every registered member |
| Refusing all edits in generated files | Superseded by explicit `source: xml` versus `source: manual` ownership |
| Upstream SDL Markdown normalization and external-link remapping | Retired with excluded third-party/backend member reference generation; integration guides and legal provenance remain |

The unused Docs source-certificate inspection script and its tests were removed with the retired paired publication chain. Current publication tests retain exact producer, source tree, artifact digest, missing-byte and tampering checks without requiring Engine functional certification.
